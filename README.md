# Личная CRM

Приложение, где я веду контакты людей, которых знаю лично. Подробности — в `specs/01-продуктовая-идея.md`.

## Что умеет

- Вход по ссылке из письма, пароля нет. На странице входа вводишь почту и нажимаешь «Получить ссылку» — на почту приходит письмо «Вход в Личную CRM» с кнопкой «Войти». Первый вход и есть регистрация, имя не спрашиваем. Ссылка работает один раз и 15 минут, новая ссылка отменяет прежние, на одну почту уходит не больше 3 писем за 10 минут. Большие и маленькие буквы в почте не различаются, пробелы по краям убираются
- Вход держится 30 дней с последнего захода на этом устройстве, можно быть внутри с нескольких устройств сразу. В шапке каждой страницы — твоя почта и кнопка «Выйти»: она завершает вход только на этом устройстве. Без входа не открывается ни одна страница, кроме страницы входа (и адреса `/health` для проверки выкатки)
- У каждого свои данные: контакты, заметки и группы принадлежат тому, кто их завёл, и больше никто их не видит — ни в списке, ни в поиске, ни в счётчике, ни в «Пора связаться». Чужой контакт по прямой ссылке открывается так же, как несуществующий, — «Контакт не найден». Права проверяет сервер в каждом запросе, а не только интерфейс
- Новый пользователь видит пустой список с подсказкой «Добавьте первый контакт»
- Список всех контактов по алфавиту, с разбивкой по буквам
- Поиск по имени: по части имени, без учёта регистра, «е» и «ё» не различаются («семен» найдёт «Семёнов»)
- Добавление контакта: имя, кто это, откуда знакомы, телефон, почта
- Карточка контакта: все поля, кнопки «Изменить» и «Удалить» и заметки с датой — что обсудили и о чём договорились
- Частота общения: в форме контакта поле «Как часто общаться» — раз в неделю, месяц, квартал, год или свой срок (раз в N дней, от 1 до 365). Срок считается от последней заметки, а если заметок нет — от того дня, когда частоту задали или сменили
- Блок «Пора связаться» на главной над списком: контакты, с которыми не общались дольше срока, сверху самые просроченные. Если просроченных нет или идёт поиск, блока нет
- В карточке строка «Как часто общаться»: частота и дата, до которой надо связаться, а у просроченного — красным, на сколько дней просрочено
- Галочка «Пообщались» в блоке и в карточке: добавляет заметку «Пообщались», срок отсчитывается заново. Пять секунд после нажатия в уведомлении можно нажать «Отменить» — заметка удалится
- Удаление контакта — только после подтверждения; удаляется насовсем вместе со всеми его заметками
- Группы: в форме контакта поле «Группы» — отметки у существующих групп и поле «Новая группа» с кнопкой «Добавить». Новая группа создаётся, когда сохраняешь контакт; если отменить форму, группа не появится. Контакт может быть в нескольких группах или ни в одной
- В карточке строка «Группы»: названия групп по алфавиту, а если групп нет — «Не указано»
- Фильтр по группам на главной: над списком кнопка «Все» и кнопка каждой группы. Можно выбрать несколько — останутся контакты, которые входят во все выбранные группы. Работает вместе с поиском по имени, выбор сохраняется в адресе страницы. Пока включена группа, блока «Пора связаться» нет
- Страница «Группы» (ссылка «Управление группами» над списком, когда группы есть): все группы по алфавиту с числом контактов, название ведёт на список с включённым фильтром. Группу можно переименовать (название не должно повторять другую твою группу без учёта регистра и «е»/«ё»; у разных людей группы могут называться одинаково) и удалить — только после подтверждения; контакты остаются, просто выходят из группы
- Данные хранятся в базе PostgreSQL, поэтому в любом браузере, где ты вошёл под той же почтой, видны одни и те же контакты

Запущенное на этом компьютере приложение открывается только на нём, поэтому из сети (например, из того же Wi‑Fi) оно недоступно. Письма со ссылками для входа на настоящие адреса не уходят: они остаются в Mailpit на этом компьютере (<http://localhost:8025>), а войти можно под любым адресом, даже выдуманным.

Версия на сервере — <https://app.context-crm.site> — пускает только по ссылке из письма: письма уходят на настоящие адреса через Resend. Друзья регистрируются сами (первый вход и есть регистрация) и видят только свои данные. Контакты, которые были в базе до входа (тестовые данные), достались владельцу — пользователю с почтой из `OWNER_EMAIL` на сервере. Как приложение выкатывается — в разделе [«Выкатка на сервер»](#выкатка-на-сервер).

## Как запустить

### Что нужно

- Docker (OrbStack или Docker Desktop) — должен быть запущен
- Node.js 24 и pnpm

### Первый запуск

1. Создай файл с настройками из шаблона и заполни значения:

   ```bash
   cp .env.example .env
   ```

   Пароль — любая длинная случайная строка, например из `openssl rand -hex 24`.
   `DATABASE_URL` собирается из тех же значений, формат указан в шаблоне.

   Для входа в приложение нужны ещё пять строк:

   | Строка               | Что это                                                                             | Что вписать на компьютере                        |
   | -------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------ |
   | `BETTER_AUTH_SECRET` | секрет, которым приложение подписывает вход                                         | случайная строка из `openssl rand -base64 32`    |
   | `BETTER_AUTH_URL`    | адрес, по которому открываешь приложение; кука входа привязана к нему               | `http://localhost:3000`                          |
   | `SMTP_URL`           | куда отправлять письма со ссылкой для входа; на компьютере это Mailpit              | `smtp://127.0.0.1:1025`                          |
   | `MAIL_FROM`          | от кого письмо                                                                      | `Личная CRM <noreply@mail.crm.context-crm.site>` |
   | `OWNER_EMAIL`        | почта владельца: ему достаются прежние контакты, у него создаются тестовые контакты | твоя почта                                       |

   Приложение открывай именно по адресу `http://localhost:3000`, как в `BETTER_AUTH_URL`: для браузера `localhost` и `127.0.0.1` — разные адреса, и вход, сделанный на одном, на другом не виден.

2. Запусти базу и почтовую заглушку Mailpit:

   ```bash
   docker compose up -d
   ```

   Проверь, что они работают: `docker compose ps` — у базы в колонке `STATUS` должно быть `healthy`, у `mailpit` — `Up`.

   Mailpit ловит все письма приложения, на настоящие адреса они не уходят. Его страница — <http://localhost:8025>: там лежат письма со ссылками для входа. Войти можно под любым адресом, даже выдуманным.

3. Установи зависимости и создай таблицы в базе:

   ```bash
   pnpm install
   pnpm db:migrate
   ```

   `pnpm db:migrate` запускает тот же скрипт (`scripts/migrate.ts`), что и сервер при выкатке. Если в базе уже есть контакты или группы (они появились до входа), у них должен быть владелец: миграция отдаёт их пользователю с почтой из `OWNER_EMAIL`. Без этой строки при данных в базе миграция остановится с понятной ошибкой, а база останется как была. В пустой базе почта не нужна.

4. По желанию — заполни базу тестовыми данными (1000 выдуманных контактов с заметками):

   ```bash
   pnpm db:seed
   ```

   Контакты создаются у владельца — пользователя с почтой из `OWNER_EMAIL` (если его ещё нет, он создаётся). Чтобы их увидеть, войди под этой почтой; другой пользователь их не увидит. Команда ничего не удаляет и не перезаписывает: если у владельца уже есть контакты, она просто ничего не сделает.
   Все люди выдуманные, почты — на служебных доменах `example.com`, письмо на них никуда не уйдёт.

5. Собери и запусти приложение:

   ```bash
   pnpm build
   pnpm start
   ```

   Открой в браузере: <http://localhost:3000>. Остановить — `Ctrl+C` в терминале.

### Следующие запуски

```bash
docker compose up -d   # если база и Mailpit не запущены
pnpm start             # если код не менялся; после изменений сначала pnpm build
```

## Как проверить главный сценарий руками

1. Открой <http://localhost:3000> — видна страница входа. Введи почту (любую, например `me@example.com`) и нажми «Получить ссылку». Открой Mailpit (<http://localhost:8025>), в письме «Вход в Личную CRM» нажми «Войти» — ты внутри, в шапке твоя почта
2. На главной видно список контактов и их число
3. Нажми «Добавить контакт», заполни имя, нажми «Добавить контакт» — откроется список, новый контакт подсвечен жёлтым
4. Начни вводить его имя в поиске — список отфильтруется
5. Открой контакт, напиши заметку, нажми «Добавить заметку» — заметка появится ниже с датой
6. Обнови страницу — заметка на месте
7. Открой тот же адрес в другом браузере (например, Safari), войди под той же почтой (новое письмо в Mailpit) — те же контакты и та же заметка

## Для разработки

- `pnpm dev` — режим разработки: изменения в коде видны сразу, но страницы открываются медленнее
- `pnpm lint` и `pnpm typecheck` — проверка кода
- `pnpm format` — привести оформление кода к единому виду (Prettier); `pnpm format:check` — только проверить, ничего не меняя
- `pnpm test` — unit-тесты (Vitest): проверяют правила приложения без браузера и базы, за секунду. Лежат рядом с кодом, файлы `*.test.ts`
- `pnpm test:db` — тесты на настоящей базе (Vitest): проверяют код, который читает и пишет данные, например что один человек не видит и не меняет чужое. Лежат рядом с кодом, файлы `*.db.test.ts`. Нужна запущенная база (`docker compose up -d`). Перед прогоном создаётся пустая база `personal_crm_test` (рядом с твоей, твои контакты не трогает) и применяются миграции. Обычный `pnpm test` эти файлы не берёт
- `pnpm test:e2e` — e2e-тесты: робот-браузер проходит сценарии как человек (подробнее ниже)
- `pnpm db:generate` — после изменения схемы в `src/db/schema.ts` создаёт новую миграцию в папке `drizzle/`, затем `pnpm db:migrate` применяет её (тем же скриптом, что и сервер)

Где что лежит:

- `src/app` — страницы: список (`page.tsx`), новый контакт, карточка, редактирование; `actions.ts` — сохранение данных
- `src/db` — схема таблиц, подключение к базе, запросы
- `src/components` — формы, поиск и другие части интерфейса
- `src/styles/tokens.css` — дизайн-токены: цвета, шрифты, размеры текста, тени. Оформление общее с лендингом, токены взяты из него
- `src/app/health` — адрес `/health` для проверки после выкатки
- `scripts` — заполнение базы тестовыми данными и применение миграций на сервере
- `e2e` — e2e-тесты и подготовка тестовой базы; `playwright.config.ts` — как они запускаются
- `Dockerfile` — как собирается образ приложения для сервера
- `.github/workflows/ci.yml` — проверки каждого PR (подробнее ниже)
- `.github/workflows/deploy.yml` — автовыкатка: сборка образа и запуск скриптов на сервере
- `deploy` — всё, что работает на сервере: `compose.yaml`, скрипты выкатки и отката, настройка nginx, разовая подготовка сервера
- `openspec` — требования фич: `specs` — как приложение работает сейчас, `changes` — фичи в работе, `config.yaml` — что OpenSpec знает о проекте (язык спек — русский, стек, правила)

### e2e-тесты

Каждый тест сначала входит под своей почтой (`…-<случайное>@example.com`) через настоящую форму и настоящее письмо: ссылку тест берёт из Mailpit, поэтому тесты не мешают друг другу и настоящих писем не отправляют. Вход делает `e2e/fixtures.ts`, работу с Mailpit — `e2e/mailpit.ts`.

Тест главного сценария (`e2e/main-scenario.spec.ts`) открывает приложение в браузере и делает то же, что раздел «Как проверить главный сценарий руками» выше: входит, видит список, добавляет контакт, находит его, пишет заметку, обновляет страницу и открывает тот же адрес в чистом браузере, войдя под той же почтой.

Тесты входа (`e2e/login.spec.ts`) проходят сценарии из `openspec/specs/user-auth/spec.md`: страницу входа, письмо, ссылку (один раз, 15 минут, только последняя), лимит писем, срок входа, шапку и выход. Время они двигают прямо в тестовой базе, а отказ почтового сервиса изображают режимом Chaos у Mailpit. Не проверяется только сценарий «На сервере»: его я прохожу руками после выкатки.

Тесты «Не терять связь» (`e2e/keep-in-touch.spec.ts`) проходят сценарии из `openspec/specs/keep-in-touch/spec.md`: частота в формах, блок «Пора связаться», заметка и галочка «Пообщались» с отменой, начало отсчёта срока. Каждый шаг теста называется по сценарию, поэтому в отчёте видно, какой сценарий сломался. Просроченные контакты тест кладёт прямо в тестовую базу с датами в прошлом, а перед каждым тестом очищает её.

Тесты групп (`e2e/contact-groups.spec.ts`) проходят сценарии из `openspec/specs/contact-groups/spec.md`: группы в форме и в карточке, фильтр на главной, удаление группы и контакта. Переименование группы и переход со страницы «Группы» на фильтр e2e-тестами не покрыты: их проверяем руками.

Первый раз на компьютере скачай браузер для тестов:

```bash
pnpm exec playwright install chromium
```

Запуск — база в Docker должна работать (`docker compose up -d`):

```bash
pnpm test:e2e
```

Что происходит: собирается приложение из текущего кода, создаётся пустая тестовая база `personal_crm_e2e` (рядом с твоей, твои контакты не трогает), применяются миграции, приложение запускается на <http://127.0.0.1:3100>, браузер проходит сценарий, приложение останавливается.

Если тест упал — в `test-results/` лежат снимок экрана и запись шагов; отчёт в браузере: `pnpm exec playwright show-report`.

### Проверки PR (CI)

На каждый PR GitHub Actions сам запускает три проверки (`.github/workflows/ci.yml`):

- **Lint, format, types, unit tests** — `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`
- **e2e tests** — `pnpm test:db` и `pnpm test:e2e` на настоящей PostgreSQL и почтовой заглушке Mailpit, которые живут только во время проверки
- **Docker image** — сборка образа приложения, как при выкатке, но образ никуда не отправляется

Ветка `main` защищена: в неё попадают только через PR, и только когда все три проверки зелёные. Напрямую в `main` не запушить — даже владельцу.

PR вливается сам (автовлитие): после открытия PR агент включает его командой `gh pr merge --auto --squash`, и как только проверки позеленеют, GitHub вливает PR — а влитие в `main` запускает выкатку. Если проверка красная — PR ждёт, пока причину починят.

Где смотреть: в PR внизу блок проверок, или в терминале `gh pr checks --watch`. Если упали e2e-тесты — на странице запуска (**Details** → **Summary**) внизу архив `playwright-report` со снимком экрана и записью шагов.

Проверь у себя то же, что проверит CI, до пуша:

```bash
pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && pnpm test:db && pnpm test:e2e
```

### Как делаем фичи (OpenSpec)

Требования к фичам пишем в [OpenSpec](https://openspec.dev): сначала агент описывает, что и зачем меняем, потом — план, потом делает по шагам.

На новом компьютере один раз поставь программу `openspec` (Node.js для неё не нужен):

```bash
curl -fsSL https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/scripts/binary/install.sh | sh
openspec --version
```

Команды в Claude Code:

- `/opsx:explore` — обсудить идею, пока непонятно, что именно делать
- `/opsx:propose <имя-фичи>` — описать фичу: зачем, требования со сценариями, как сделать, список задач
- `/opsx:apply` — сделать фичу по списку задач
- `/opsx:archive` — фича готова: её требования переносятся в `openspec/specs`

Обновить OpenSpec: ещё раз команда установки выше, затем `openspec update` в папке проекта.

## Полезные команды для базы

- Остановить базу: `docker compose stop` — данные сохранятся
- Запустить снова: `docker compose up -d`
- Открыть консоль базы: `docker compose exec db psql -U personal_crm -d personal_crm` (выход — `\q`)
- **Осторожно:** `docker compose down -v` удаляет базу вместе со всеми данными

## Выкатка на сервер

Приложение работает на сервере `62.109.29.244` по адресу <https://app.context-crm.site>.

### Как выкатить новую версию

1. Изменения попадают в `main` только через PR: когда проверки PR зелёные, он вливается сам (см. [«Проверки PR (CI)»](#проверки-pr-ci)), и влитие запускает выкатку. Больше ничего делать не нужно
2. Посмотри, как идёт выкатка: на GitHub вкладка **Actions** → **Deploy**, или в терминале `gh run watch`. Обычно она занимает 3–5 минут
3. Зелёная галочка — новая версия на сервере. Красный крестик — выкатка упала: открой упавший шаг, в последних строках написано, что пошло не так
4. Проверь: открой <https://app.context-crm.site/health> — должно быть `"status":"ok"`, а `version` совпадает с номером последнего коммита (`git rev-parse HEAD`)

### Что происходит при выкатке

1. GitHub Actions собирает Docker-образ приложения с тегом — номером (SHA) коммита и кладёт его в GitHub Container Registry: `ghcr.io/valerakus/personal-crm`
2. Копирует папку `deploy` на сервер в `/srv/personal-crm` и запускает там `deploy.sh`, который:
   - скачивает новый образ
   - делает бэкап базы (подробнее — в разделе [«Бэкапы и восстановление»](#бэкапы-и-восстановление)). Не получился — выкатка останавливается, работает прежняя версия
   - запускает из нового образа разовый контейнер, который применяет миграции базы и завершается. Если миграции упали — выкатка останавливается, работает прежняя версия
   - запускает приложение из нового образа
   - проверяет `/health` через nginx и HTTPS: адрес должен ответить 200 и назвать новую версию
   - удаляет старые образы: на сервере остаются только текущий и предыдущий
3. Одновременно идёт только одна выкатка: следующий push ждёт, пока закончится текущая

Сам скрипт ничего не откатывает: если выкатка упала, всё остаётся как есть, решение — за мной.

### Как работать с сервером

Все команды — под пользователем `deploy`, от которого работает приложение:

```bash
ssh crm
sudo -iu deploy
cd /srv/personal-crm
```

- Что запущено: `docker compose ps`
- Логи приложения: `docker compose logs --tail 100 app`
- **Откат** на предыдущую версию: `./rollback.sh`. Миграции базы при этом не откатываются. Повторный запуск возвращает версию, с которой откатились. Исключение — выкатка со входом, её откатывают только целиком, см. [«Откат выкатки со входом»](#откат-выкатки-со-входом)
- Заполнить базу тестовыми данными владельца (`OWNER_EMAIL` из `.env` на сервере): `docker compose run --rm migrate node scripts/seed.js`. Если у владельца уже есть контакты, команда ничего не делает
- Бэкап базы вручную: `./backup.sh`
- Восстановить базу из бэкапа: `./restore.sh backups/<файл>` (см. [ниже](#бэкапы-и-восстановление))
- Выйти: `exit` два раза

Что лежит в `/srv/personal-crm`:

- `.env` — пароль базы и настройки входа, права 600: читает только `deploy`. В git его нет, создаётся вручную один раз:

  ```
  POSTGRES_USER=personal_crm
  POSTGRES_PASSWORD=длинная случайная строка из латинских букв и цифр
  POSTGRES_DB=personal_crm
  BETTER_AUTH_SECRET=случайная строка из `openssl rand -base64 32`
  SMTP_URL=smtps://resend:<ключ Resend>@smtp.resend.com:465
  OWNER_EMAIL=твоя почта
  ```

  Последние три строки нужны для входа. Без любой из них выкатка остановится на первом же шаге, до бэкапа и миграций, и продолжит работать прежняя версия. `OWNER_EMAIL` — почта, которой достаются контакты, что были в базе до входа, и тестовые контакты; пиши её точно: при опечатке данные уйдут другому пользователю. Адрес приложения (`BETTER_AUTH_URL`) и отправитель писем (`MAIL_FROM`) записаны прямо в `compose.yaml`

- `compose.yaml` и скрипты — копия папки `deploy`, обновляется при каждой выкатке
- `backups/` — бэкапы базы, права 700
- `compose.override.yaml` — какая версия работает сейчас, `previous-release.yaml` — предыдущая. Их пишут скрипты выкатки и отката

### Письма со ссылками для входа (Resend)

Письма на сервере уходят через [Resend](https://resend.com) по SMTP, с адреса `noreply@mail.crm.context-crm.site` от имени «Личная CRM». Настраивается один раз:

1. Заведи аккаунт на resend.com и добавь домен `mail.crm.context-crm.site` (раздел **Domains**)
2. Resend покажет записи DNS (SPF, DKIM и другие). Добавь их в панели reg.ru для этого домена и нажми **Verify** — домен должен стать **Verified**. Без этого письма уходят в спам или не доходят
3. В разделе **API Keys** создай ключ с правом только на отправку (**Sending access**) для этого домена
4. В `/srv/personal-crm/.env` на сервере впиши строку `SMTP_URL=smtps://resend:<ключ>@smtp.resend.com:465` (логин всегда `resend`, пароль — ключ), а также `BETTER_AUTH_SECRET` и `OWNER_EMAIL` (см. выше). Ключ нигде больше не храним и в чат не присылаем
5. Выкати приложение (merge PR) и проверь: открой <https://app.context-crm.site>, введи свою почту — письмо «Вход в Личную CRM» придёт в настоящий ящик, кнопка «Войти» впустит, и ты увидишь свои прежние контакты

Если письмо не пришло: сначала папка «Спам», потом `docker compose logs --tail 100 app` на сервере — там видно, принял ли Resend письмо, а в панели Resend (**Emails**) — что с ним стало.

### Откат выкатки со входом

Эту выкатку нельзя откатить одним `./rollback.sh`: она меняет базу (контакты получают владельца), а прошлая версия приложения про владельцев не знает. Откатывать можно только целиком и только вручную, в таком порядке:

1. `./restore.sh backups/<бэкап этой выкатки>` — база возвращается к состоянию до выкатки. Бэкап этой выкатки — файл, который `deploy.sh` снял первым шагом, до миграций: самый свежий в `backups/` на момент выкатки (`ls -lt backups`), в его имени версия — та, что работала до входа. Запиши имя файла сразу после выкатки
2. `./rollback.sh` — возвращается прошлая версия приложения

Порядок важен. Пока новая версия работает на старой базе, она выдаёт ошибки, но ничего не показывает. А прошлая версия на новой базе несколько минут показывала бы всем контакты владельца: входа в ней нет.

**Осторожно:** всё, что друзья внесут после выкатки, при таком откате пропадёт. `restore.sh` перед восстановлением снимает копию текущей базы (`backups/before-restore-…`), данные из неё можно достать вручную.

### Бэкапы и восстановление

Бэкап делается автоматически первым шагом каждой выкатки, до миграций. Файлы лежат на сервере в `/srv/personal-crm/backups`, называются `db-<дата>-<время>-<версия>.sql.gz`: версия — та, что работала **до** выкатки (при самой первой выкатке — `none`). Хранятся последние 14, старые удаляются сами.

Посмотреть бэкапы:

```bash
ssh crm
sudo -iu deploy
cd /srv/personal-crm
ls -lh backups
```

Восстановить базу из бэкапа:

```bash
./restore.sh backups/db-20261107-153000-<версия>.sql.gz
```

Что делает `restore.sh`:

1. Показывает, какой файл какую базу заменит, и ждёт, пока ты напишешь `yes`. Что-то другое — ничего не меняется
2. Снимает копию текущей базы: `backups/before-restore-<дата>-<версия>.sql.gz` (такие копии сами не удаляются)
3. Останавливает приложение, удаляет базу, создаёт пустую и загружает бэкап
4. Запускает приложение той же версии, что работала, и проверяет `/health`

**Осторожно:** база заменяется целиком — всё, что добавлено после бэкапа, пропадёт (кроме копии из пункта 2). Версия приложения не меняется. Если что-то пошло не так, скрипт останавливается и пишет, что случилось; сам он ничего не откатывает.

### Что настроено один раз

- На сервере: пользователь `deploy` (может запускать Docker, без sudo), папка `/srv/personal-crm`, nginx передаёт запросы к app.context-crm.site приложению. Всё это делает `deploy/setup-server.sh`
- В настройках репозитория на GitHub (**Settings** → **Secrets and variables** → **Actions**): секрет `DEPLOY_SSH_KEY` — ключ, которым GitHub заходит на сервер как `deploy`, и переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` — адрес сервера, пользователь и отпечаток сервера
- Время в заметках показывается по часовому поясу `Europe/Zurich` — строка `TZ` в `deploy/compose.yaml`
