# Личная CRM

Приложение, где я веду контакты людей, которых знаю лично. Подробности — в `specs/01-продуктовая-идея.md`.

## Что умеет

- Список всех контактов по алфавиту, с разбивкой по буквам
- Поиск по имени: по части имени, без учёта регистра, «е» и «ё» не различаются («семен» найдёт «Семёнов»)
- Добавление контакта: имя, кто это, откуда знакомы, телефон, почта
- Карточка контакта: все поля, кнопки «Изменить» и «Удалить» и заметки с датой — что обсудили и о чём договорились
- Удаление контакта — только после подтверждения; удаляется насовсем вместе со всеми его заметками
- Данные хранятся в базе PostgreSQL, поэтому в любом браузере на этом компьютере видны одни и те же контакты

Запущенное на этом компьютере приложение открывается только на нём: входа по паролю нет, поэтому из сети (например, из того же Wi‑Fi) оно недоступно.

Версия на сервере — <https://app.context-crm.site> — открыта всем, кто знает адрес: входа нет, любой может смотреть и менять контакты. Поэтому там только тестовые данные, настоящие контакты туда не вносим, пока не решим, как её защитить. Как она выкатывается — в разделе [«Выкатка на сервер»](#выкатка-на-сервер).

## Как запустить

### Что нужно

- Docker (OrbStack или Docker Desktop) — должен быть запущен
- Node.js 24 и pnpm

### Первый запуск

1. Создай файл с настройками из шаблона и заполни значения:

   ```bash
   cp .env.example .env
   ```

   Пароль — любая длинная случайная строка, например из `openssl rand -hex 24`.
   `DATABASE_URL` собирается из тех же значений, формат указан в шаблоне.

2. Запусти базу:

   ```bash
   docker compose up -d
   ```

   Проверь, что она работает: `docker compose ps` — в колонке `STATUS` должно быть `healthy`.

3. Установи зависимости и создай таблицы в базе:

   ```bash
   pnpm install
   pnpm db:migrate
   ```

4. По желанию — заполни базу тестовыми данными (1000 выдуманных контактов с заметками):

   ```bash
   pnpm db:seed
   ```

   Команда ничего не удаляет и не перезаписывает: если в базе уже есть контакты, она просто ничего не сделает.
   Все люди выдуманные, почты — на служебных доменах `example.com`, письмо на них никуда не уйдёт.

5. Собери и запусти приложение:

   ```bash
   pnpm build
   pnpm start
   ```

   Открой в браузере: <http://localhost:3000>. Остановить — `Ctrl+C` в терминале.

### Следующие запуски

```bash
docker compose up -d   # если база не запущена
pnpm start             # если код не менялся; после изменений сначала pnpm build
```

## Как проверить главный сценарий руками

1. Открой <http://localhost:3000> — видно список всех контактов и их число
2. Нажми «Добавить контакт», заполни имя, нажми «Добавить контакт» — откроется список, новый контакт подсвечен жёлтым
3. Начни вводить его имя в поиске — список отфильтруется
4. Открой контакт, напиши заметку, нажми «Добавить заметку» — заметка появится ниже с датой
5. Обнови страницу — заметка на месте
6. Открой тот же адрес в другом браузере (например, Safari) — те же контакты и та же заметка

## Для разработки

- `pnpm dev` — режим разработки: изменения в коде видны сразу, но страницы открываются медленнее
- `pnpm lint` и `pnpm typecheck` — проверка кода
- `pnpm db:generate` — после изменения схемы в `src/db/schema.ts` создаёт новую миграцию в папке `drizzle/`, затем `pnpm db:migrate` применяет её

Где что лежит:

- `src/app` — страницы: список (`page.tsx`), новый контакт, карточка, редактирование; `actions.ts` — сохранение данных
- `src/db` — схема таблиц, подключение к базе, запросы
- `src/components` — формы, поиск и другие части интерфейса
- `src/styles/tokens.css` — дизайн-токены: цвета, шрифты, размеры текста, тени. Оформление общее с лендингом, токены взяты из него
- `src/app/health` — адрес `/health` для проверки после выкатки
- `scripts` — заполнение базы тестовыми данными и применение миграций на сервере
- `Dockerfile` — как собирается образ приложения для сервера
- `.github/workflows/deploy.yml` — автовыкатка: сборка образа и запуск скриптов на сервере
- `deploy` — всё, что работает на сервере: `compose.yaml`, скрипты выкатки и отката, настройка nginx, разовая подготовка сервера

## Полезные команды для базы

- Остановить базу: `docker compose stop` — данные сохранятся
- Запустить снова: `docker compose up -d`
- Открыть консоль базы: `docker compose exec db psql -U personal_crm -d personal_crm` (выход — `\q`)
- **Осторожно:** `docker compose down -v` удаляет базу вместе со всеми данными

## Выкатка на сервер

Приложение работает на сервере `62.109.29.244` по адресу <https://app.context-crm.site>.

### Как выкатить новую версию

1. Закоммить изменения и сделай push в ветку `main`. Больше ничего делать не нужно
2. Посмотри, как идёт выкатка: на GitHub вкладка **Actions** → **Deploy**, или в терминале `gh run watch`. Обычно она занимает 3–5 минут
3. Зелёная галочка — новая версия на сервере. Красный крестик — выкатка упала: открой упавший шаг, в последних строках написано, что пошло не так
4. Проверь: открой <https://app.context-crm.site/health> — должно быть `"status":"ok"`, а `version` совпадает с номером последнего коммита (`git rev-parse HEAD`)

### Что происходит при выкатке

1. GitHub Actions собирает Docker-образ приложения с тегом — номером (SHA) коммита и кладёт его в GitHub Container Registry: `ghcr.io/valerakus/personal-crm`
2. Копирует папку `deploy` на сервер в `/srv/personal-crm` и запускает там `deploy.sh`, который:
   - скачивает новый образ
   - запускает из него разовый контейнер, который применяет миграции базы и завершается. Если миграции упали — выкатка останавливается, работает прежняя версия
   - запускает приложение из нового образа
   - проверяет `/health` через nginx и HTTPS: адрес должен ответить 200 и назвать новую версию
   - удаляет старые образы: на сервере остаются только текущий и предыдущий
3. Одновременно идёт только одна выкатка: следующий push ждёт, пока закончится текущая

Сам скрипт ничего не откатывает: если выкатка упала, всё остаётся как есть, решение — за мной.

### Как работать с сервером

Все команды — под пользователем `deploy`, от которого работает приложение:

```bash
ssh crm
sudo -iu deploy
cd /srv/personal-crm
```

- Что запущено: `docker compose ps`
- Логи приложения: `docker compose logs --tail 100 app`
- **Откат** на предыдущую версию: `./rollback.sh`. Миграции базы при этом не откатываются. Повторный запуск возвращает версию, с которой откатились
- Заполнить пустую базу тестовыми данными: `docker compose run --rm migrate node scripts/seed.js`. Если контакты уже есть, команда ничего не делает
- Выйти: `exit` два раза

Что лежит в `/srv/personal-crm`:

- `.env` — пароль базы, права 600: читает только `deploy`. В git его нет, создаётся вручную один раз:

  ```
  POSTGRES_USER=personal_crm
  POSTGRES_PASSWORD=длинная случайная строка из латинских букв и цифр
  POSTGRES_DB=personal_crm
  ```

- `compose.yaml` и скрипты — копия папки `deploy`, обновляется при каждой выкатке
- `compose.override.yaml` — какая версия работает сейчас, `previous-release.yaml` — предыдущая. Их пишут скрипты выкатки и отката

### Что настроено один раз

- На сервере: пользователь `deploy` (может запускать Docker, без sudo), папка `/srv/personal-crm`, nginx передаёт запросы к app.context-crm.site приложению. Всё это делает `deploy/setup-server.sh`
- В настройках репозитория на GitHub (**Settings** → **Secrets and variables** → **Actions**): секрет `DEPLOY_SSH_KEY` — ключ, которым GitHub заходит на сервер как `deploy`, и переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` — адрес сервера, пользователь и отпечаток сервера
- Время в заметках показывается по часовому поясу `Europe/Zurich` — строка `TZ` в `deploy/compose.yaml`
