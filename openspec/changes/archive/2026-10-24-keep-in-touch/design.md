# Design

## Context

- Зачем — см. `proposal.md`, что должно работать — см. `specs/keep-in-touch/spec.md`, как выглядит — макет из `proposal.md`, раздел Mockups, и его копия в `mockups/`.
- Сейчас в базе две таблицы: `contacts` и `notes`. Заметки нельзя ни изменить, ни удалить, только добавить; у `notes` уже есть индекс по `(contact_id, created_at)`.
- Даты заметок форматируются на сервере в часовом поясе процесса Node. На сервере он задан в `deploy/compose.yaml`: `TZ: Europe/Zurich`; локально — пояс компьютера.
- Главная (`src/app/page.tsx`) и карточка (`src/app/contacts/[id]/page.tsx`) всегда читают свежие данные (`force-dynamic`). `addNote` обновляет карточку через `revalidatePath`.
- Формы добавления и изменения — общий `ContactForm`, проверка полей — `contactSchema` в `src/lib/validation.ts`, поля формы перечислены в `CONTACT_FIELDS` в `src/app/actions.ts`.
- Уведомления — `sonner`, `<Toaster position="bottom-center">` уже стоит в `src/app/layout.tsx`.
- Автотестов и библиотек для них в проекте нет. Новую библиотеку без согласования добавлять нельзя.

## Goals / Non-Goals

**Goals:**

- Одно место, где живут правила срока; его используют и блок на главной, и карточка — чтобы они никогда не расходились.
- Миграция только добавляет поля: старые данные не меняются, предыдущая версия приложения работает с новой базой.
- Галочка «Пообщались» — обычная заметка: никакого второго источника «последнего общения».

**Non-Goals:**

- Хранить дату последнего общения отдельным полем — она вычисляется из заметок.
- Удаление и правка заметок в целом — отмена удаляет только свежую заметку «Пообщались».
- Автотесты — для них нужна новая библиотека, это отдельное решение.

## Decisions

### 1. Три поля в `contacts`

- `keep_in_touch_frequency` — `text`, может быть пустым (NULL = «Не задано»). `CHECK`: только `week`, `month`, `quarter`, `year`, `days`.
- `keep_in_touch_days` — `smallint`, может быть пустым: N для своего срока. `CHECK`: от 1 до 365; заполнено тогда и только тогда, когда частота — `days`: `(keep_in_touch_frequency IS NOT DISTINCT FROM 'days') = (keep_in_touch_days IS NOT NULL)`.
- `keep_in_touch_since` — `timestamptz`, может быть пустым: момент, когда частоту последний раз задали или сменили. `CHECK`: заполнено тогда и только тогда, когда частота задана.

Почему так:

- `text` + `CHECK`, а не `pgEnum`: значение в enum Postgres потом трудно убрать или переименовать, а `CHECK` меняется обычной миграцией.
- Свой срок — отдельное число, а не «всё в днях»: месяц, квартал и год календарные, их нельзя выразить фиксированным числом дней.
- Поля в `contacts`, а не отдельная таблица: у контакта ровно одна частота.
- Дату последней заметки не храним, а считаем как `max(notes.created_at)`: копия даты могла бы разойтись с заметками, а индекс для подсчёта уже есть.

### 2. Когда меняется `keep_in_touch_since`

- `createContact`: частота выбрана → `since = now()`, нет → все три поля пустые.
- `updateContact`: одним `UPDATE` с `CASE`. Если новая частота или новое N отличаются от сохранённых (`IS DISTINCT FROM`), `since = now()`, а при «Не задано» — NULL. Если не отличаются, `since` не трогаем.
- Почему одним `UPDATE`, а не «прочитать, сравнить, записать»: нет гонки между чтением и записью, а сравнение со значением в базе гарантирует, что сохранение формы без смены частоты срок не сдвигает.

### 3. Правила срока — один модуль на TypeScript

`src/lib/keep-in-touch.ts` — без обращений к базе:

- список частот и подписи: `week` → «Раз в неделю» и т. д.; `days` → «Раз в N дней» со склонением через существующий `pluralize`, при N = 1 — «Каждый день»
- функция, которая по частоте, N, `since`, дате последней заметки и «сейчас» возвращает дату срока и число дней просрочки, а для «Не задано» — ничего
- начало отсчёта: дата последней заметки, а если заметок нет — `since`
- календарная дата берётся локальными методами `Date` (`getFullYear`, `getMonth`, `getDate`): они работают в часовом поясе процесса — том же, в котором показываются даты заметок
- месяцы прибавляются с поправкой на конец месяца: 31 января + месяц = последний день февраля; неделя — плюс 7 дней, свой срок — плюс N дней
- дни просрочки — разница между двумя календарными датами через `Date.UTC(y, m, d)`: так переход на летнее и зимнее время не даёт сбоя на сутки

Почему не SQL: Postgres тоже умеет прибавлять календарные месяцы, но сессия базы на сервере работает в UTC, а карточке всё равно нужен тот же расчёт в коде. Два расчёта в двух местах рано или поздно разойдутся. Контактов с частотой немного, считать их в коде дёшево.

### 4. Запрос для блока

Новая функция в `src/db/queries.ts` берёт контакты с заданной частотой:

- поля: `id`, `name`, частота, N, `since`
- дата последней заметки: `max(notes.created_at)` через `LEFT JOIN` и `GROUP BY`
- порядок: по имени, в той же русской сортировке, что и общий список

Главная оставляет только просроченных и сортирует их по убыванию дней просрочки. Сортировка в JavaScript устойчивая: при равной просрочке сохраняется алфавитный порядок из запроса.

- Пока в поиске введён запрос, главная этот запрос не делает и блок не рисует.
- Карточка дату последней заметки берёт из уже загруженного списка заметок (`notes[0]`): лишнего запроса нет.

### 5. Поле в форме

- Выбор из шести вариантов кнопками-переключателями: компонент shadcn/ui `radio-group` на уже установленном `radix-ui`. Новой библиотеки нет, файл компонента добавляется в `src/components/ui/`.
- Почему не выпадающий список: шесть коротких вариантов видны сразу, выбор — одно нажатие.
- Имена полей — `keepInTouchFrequency` и `keepInTouchDays`; «Не задано» — пустое значение. Поле N видно, только когда выбран «Свой срок»: «Раз в [ N ] дней».
- Поле N — `type="text"` с `inputMode="numeric"`, а не `type="number"`: так ввод «2,5» доходит до проверки и получает понятную ошибку, а не превращается молча в пустое значение.
- `contactSchema`: перечисление из пяти значений, пустая строка — NULL. При `days` N обязательно, целое, от 1 до 365, иначе ошибка «Укажите число дней от 1 до 365» под полем N; при других частотах N — NULL.
- Форма «Изменить» получает текущие значения через `defaultValues`, как остальные поля. Поле стоит после телефона и почты.

### 6. Галочка «Пообщались» и её отмена

- Новое действие `markContacted(contactId)` в `src/app/actions.ts`: проверяет, что контакт есть, добавляет заметку с текстом «Пообщались» (одна константа на всё приложение), возвращает `id` заметки и имя контакта, обновляет главную и карточку через `revalidatePath`.
- Новое действие `undoMarkContacted(noteId)`: удаляет заметку, только если у неё текст «Пообщались» и она создана не больше минуты назад; затем то же обновление страниц. Так отмена не может удалить обычную заметку или старую отметку, даже если вызвать её с чужим `id`.
- Компонент кнопки — один на блок и карточку. В блоке — квадратная кнопка 44×44 с пиксельной галочкой справа в строке; в карточке на компьютере — галочка и подпись «Пообщались», на телефоне — только галочка. Подпись для экранных дикторов — «Пообщались: <имя>». Пока действие выполняется, кнопка недоступна: двойное нажатие не создаёт две заметки.
- В строке блока ссылка на карточку и кнопка — соседи, а не кнопка внутри ссылки: нажатие на галочку не открывает карточку.
- После успеха — `toast` из `sonner` с текстом «<имя>: отмечено «Пообщались»», кнопкой «Отменить» и длительностью 5 секунд. После отмены — короткое «Отметка отменена»; при ошибке — «Не удалось отметить» или «Не удалось отменить».
- В карточке галочка рисуется, только если частота задана.

### 7. Тексты и цвета

В `src/lib/format.ts`:

- дата срока: «12 ноября», год — только если он не текущий: «12 октября 2027»
- просрочка: «просрочено на 1 день / 3 дня / 45 дней» через уже существующий `pluralize`

Блок на главной — новый компонент в `src/components/`, в оформлении списка контактов:

- `Window` с `bar="accent"` (розовый) и `controls={3}`, видимый заголовок полосы — «пора связаться.exe»
- для экранных дикторов у раздела заголовок «Пора связаться»
- справа в полосе — число контактов
- строки — как в списке: `ContactAvatar`, имя, подпись

Красный текст просрочки — токен `--color-danger` (#C2185B, 5,9:1 на белом) в блоке и в карточке. Комментарий к токену в `src/styles/tokens.css` дополняется: теперь он ещё и для просрочки. Цвета и отступы — только через дизайн-токены.

## Risks / Trade-offs

- [Часовой пояс задан окружением, а не кодом] → Тот же пояс уже определяет даты заметок. На сервере он закреплён в `deploy/compose.yaml`, локально — пояс компьютера. Если пояс сменить, границы дней сдвинутся на несколько часов — так же, как даты заметок.
- [Блок может стать длинным: например, задал «Раз в год» многим контактам со старыми заметками — и все сразу просрочены] → Так решено, показываем всех. Если будет мешать, ограничение — отдельная правка.
- [Отмена — это удаление заметки, а удалять заметки раньше было нельзя] → Удаление ограничено одной свежей заметкой «Пообщались» (текст и возраст до минуты проверяет сервер). Обычные заметки по-прежнему не удаляются.
- [Красный цвет в приложении означал ошибку] → Так решено: просрочка — повод действовать. Текст остаётся читаемым (5,9:1), а ошибки форм отличаются местом — они под полями.
- [Автотестов нет, а расчёт дат — самое хрупкое место] → Перед готовностью прогоняем функцию на примерах из спеки разовым скриптом через уже установленный `tsx`; сам скрипт в репозиторий не кладём. Плюс проверка руками по сценариям спеки.
- [Все контакты с частотой считаются в коде при каждом открытии главной] → Для личной CRM это сотни строк, не больше. Если станет медленно, расчёт можно перенести в SQL.

## Migration Plan

1. Поменять `src/db/schema.ts`, затем `pnpm db:generate` создаст `drizzle/0001_*.sql`: три `ALTER TABLE contacts ADD COLUMN` и ограничения `CHECK`. Поля пустые, без значений по умолчанию: существующие строки не переписываются, миграция проходит мгновенно.
2. Локально — `pnpm db:migrate`.
3. На сервере, как обычно: merge в main → образ → разовый контейнер `migrate` применяет миграцию → стартует новый образ → smoke `/health`. Упала миграция — новый образ не стартует.
4. Откат — только вручную, запускает владелец (`deploy/rollback.sh`). Предыдущий образ работает с новой базой: Drizzle читает только известные ему поля, при вставке новые поля остаются пустыми, а `CHECK` пустые значения разрешают. Заметки «Пообщались» для прежней версии — обычные заметки. Поэтому миграцию при откате не трогаем. Убрать поля, если понадобится, — отдельная миграция.
