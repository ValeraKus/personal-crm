# Design

## Context

Зачем — `proposal.md`, требования — `specs/user-auth`, `specs/data-ownership`, `specs/contact-groups`.

Что есть сейчас:

- Пользователей нет. Таблицы `contacts`, `notes`, `groups`, `contact_groups` (`src/db/schema.ts`), названия групп уникальны на всю базу (индекс `groups_name_unique_idx`)
- Чтение — `src/db/queries.ts`, запись — прямо в действиях `src/app/actions.ts` через `getDb()`. Ни один запрос не знает, чей это контакт
- Страницы читают свежие данные (`force-dynamic`). Шапка с логотипом — в `src/app/layout.tsx`. Несуществующий контакт показывает общую страницу «Такой страницы нет» (`src/app/not-found.tsx`)
- Next.js 16.4: вместо `middleware.ts` — `proxy.ts`, он работает в Node.js и может ходить в базу
- Миграции на сервере применяет `scripts/migrate.ts` в разовом контейнере до старта нового образа; локально `pnpm db:migrate` запускает drizzle-kit. Бэкап перед миграциями уже делает `deploy/deploy.sh`
- e2e: Playwright собирает приложение, создаёт пустую базу `<имя>_e2e`, применяет миграции и запускает сервер на порту 3100. В CI у job `e2e` есть временный Postgres
- nginx передаёт приложению `X-Forwarded-For`. Репозиторий на GitHub публичный: личных данных в git быть не должно
- Актуальные стабильные версии на 9 ноября 2026: `better-auth` 1.7.18, `nodemailer` 10.4.0, `@types/nodemailer` 8.0.2, Mailpit v1.33.1. При установке проверить ещё раз

## Goals / Non-Goals

**Goals:**

- Забыть проверку владельца невозможно: каждая функция работы с базой требует номер владельца, функций «без владельца» нет
- Одна и та же сборка работает на компьютере, в CI и на сервере; разница — только в настройках
- Миграция существующих данных атомарна: либо у всех записей появился владелец, либо база не изменилась
- От Better Auth используем только то, что описано в его документации: внутренний формат его таблиц меняется между версиями

**Non-Goals:**

- Защита на уровне Postgres (Row Level Security)
- Библиотека Better Auth в браузере: вход и выход — действия на сервере
- Ограничение запросов по IP сверх встроенного в Better Auth
- Чистка тестовых данных на сервере, которые достанутся владельцу

## Decisions

### 1. Better Auth только на сервере

`src/lib/auth.ts` (server-only) настраивает Better Auth: адаптер Drizzle, плагины `magicLink` и `nextCookies` (последним, как требует документация), сеанс 30 дней. Секрет и адрес приложения — из `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL`. Обработчик `src/app/api/auth/[...all]/route.ts` нужен для ссылки из письма: она ведёт на `/api/auth/magic-link/verify`.

Форма входа и кнопка «Выйти» — обычные действия на сервере (`useActionState`, как остальные формы проекта). Они вызывают `auth.api.signInMagicLink` и `auth.api.signOut`, а `nextCookies` ставит куки из действия.

Отвергнуто: клиент Better Auth в браузере — лишний JavaScript и вторая схема обработки ошибок рядом с той, что уже есть в формах.

### 2. Таблицы

- Таблицы Better Auth во множественном числе: `users`, `sessions`, `accounts`, `verifications` (опция `usePlural`: так же, как `contacts` и `groups`, и без зарезервированного в Postgres слова `user`). Колонки — по схеме Better Auth той версии, что установлена. Запустить CLI Better Auth через `pnpm dlx` не удалось (скачивание и запуск пакета из сети запрещены в этой среде), поэтому схема взята из самой библиотеки (`getAuthTables` установленной версии 1.7.18), переписана в `src/db/schema.ts` в том виде, как её генерирует CLI, и проверена глазами. При обновлении Better Auth сверять заново тем же способом. Номера пользователей — текст, как по умолчанию в Better Auth
- `contacts.owner_id` и `groups.owner_id`: текст, не пустой, ссылка на `users.id` без каскада. Аккаунты не удаляются, а случайное удаление пользователя не должно уносить его контакты
- Индекс `contacts (owner_id)` для списка. Уникальный индекс групп становится `(owner_id, replace(lower(name), 'ё', 'е'))`: у A и B может быть по «Друзьям», а у одного человека дубля нет даже при двух одновременных запросах
- У `notes` и `contact_groups` своего владельца нет: они принадлежат владельцу контакта, доступ к ним — только через контакт этого владельца
- Своя таблица `login_links`: `id`, `email`, `token_hash` (SHA-256 токена ссылки), `created_at`, индекс `(email, created_at)`. По ней считается лимит писем и проверяется, что ссылка последняя (решения 4 и 5)

Отвергнуто: `owner_id` в `notes` и `contact_groups` — дублирует владельца контакта и может с ним разойтись. Составные внешние ключи «контакт и группа одного владельца» — сложнее, чем фильтр по владельцу в коде, который и так проверяют тесты.

### 3. Проверка владельца — в трёх местах

1. `src/proxy.ts` (Node.js). На каждой странице, кроме `/login…`, `/api/auth/…`, `/health` и статики, он получает сеанс через `auth.api.getSession`. Сеанса нет — переход на `/login`. Сеанс есть — пропускает запрос и передаёт в ответ куку от Better Auth с продлённым сроком. Без этого вход не продлевался бы: по документации Better Auth серверные компоненты React не могут ставить куки, и кука в браузере кончилась бы через 30 дней после входа, как бы часто человек ни заходил
2. `requireUser()` в `src/lib/session.ts` (server-only, кеш на запрос). С него начинается каждая страница и каждое действие; сеанса нет — `redirect("/login")`. Владелец всегда берётся из сеанса, а не из формы или адреса
3. Слой базы. Все чтения и записи переезжают в функции в `src/db/`, первым аргументом — `ownerId`. В каждом запросе условие `owner_id = ownerId`, для заметок и связей с группами — через контакт этого владельца. В действиях остаются проверка полей, тексты ошибок и обновление страниц. Эти функции и проверяют тесты на базе (решение 10)

Чужая запись ведёт себя как несуществующая: функция ничего не находит, действие отвечает теми же словами, что сейчас для несуществующей записи («Контакт не найден.», «Группа не найдена.», «Не удалось отменить»), удаление молча ничего не делает. Номера групп из формы и из адреса сверяются только с группами владельца. Новая страница `src/app/contacts/[id]/not-found.tsx` показывает «Контакт не найден» и для карточки, и для формы «Изменить».

Отвергнуто: Row Level Security в Postgres — самая надёжная защита, но требует транзакции с `SET LOCAL` на каждый запрос и отдельной роли базы; для этого проекта слишком тяжело. Отвергнута и проверка только в `proxy.ts`: без фильтра по владельцу в запросах вошедший B открыл бы контакт A по номеру.

### 4. Запрос ссылки: одни правила для формы и для прямого запроса

- Почту проверяет одна функция `parseLoginEmail` в `src/lib/validation.ts`: убирает пробелы по краям, переводит в нижний регистр, проверяет адрес через `z.email()`. Ошибка — «Проверьте адрес почты»
- Действие `requestLoginLink` вызывает `parseLoginEmail`, потом `auth.api.signInMagicLink` с `callbackURL: "/"` и `errorCallbackURL: "/login/link-expired"`. Ошибки Better Auth превращаются в тексты под полем
- Прямой запрос на `/api/auth/sign-in/magic-link` (в обход формы) проходит через `hooks.before` Better Auth для этого пути: та же `parseLoginEmail`, неверный адрес — ошибка 400, верный — подставляется в запрос уже приведённым
- Лимит и учёт — в `sendMagicLink({ email, token, url })`, его Better Auth вызывает при любом запросе. В транзакции с `pg_advisory_xact_lock(hashtext(email))` (два одновременных запроса не проскочат оба): писем на эту почту за 10 минут уже 3 — ошибка «Слишком часто, попробуйте через несколько минут»; иначе строка в `login_links`. Письмо отправляется после транзакции. Не ушло — строка удаляется (в лимит не идёт), ошибка «Не удалось отправить письмо, попробуйте ещё раз». Там же удаляются строки старше суток, чтобы таблица не росла
- Токен, который Better Auth успел создать до отказа по лимиту, безвреден: его никто не получил, он не попал в `login_links` и не пройдёт проверку из решения 5

Отвергнуто: встроенный лимит Better Auth — он считает по IP и адресу запроса, а не по почте. Он остаётся включённым как второй заслон, но с потолком 100 запросов в минуту вместо 5: без адреса клиента (а в e2e-тестах его нет) все запросы делят один счётчик, и 5 в минуту ломали тесты. За рассылку писем отвечает наш лимит по почте. Отвергнут и подсчёт строк в `verifications`: формат этой таблицы — внутреннее дело Better Auth.

### 5. Ссылка: 15 минут, один раз, только последняя

- `expiresIn: 900`. Один раз: Better Auth сам гасит токен при первом переходе (по документации повторный даёт `INVALID_TOKEN`)
- «Только последняя»: `hooks.before` для `/magic-link/verify` берёт `token` из адреса, ищет его хеш в `login_links`. Нет такого или у этой почты есть ссылка новее — переход на `/login/link-expired`
- Просроченную и использованную ссылку Better Auth сам отправляет на `errorCallbackURL` — ту же `/login/link-expired`. Там «Ссылка устарела, запросите новую» и кнопка «На страницу входа»
- Первый вход создаёт пользователя (`disableSignUp: false`), имя пустое, почта в нижнем регистре. Ссылка, открытая под другой почтой, создаёт новый сеанс и заменяет куку

Отвергнуто: удалять старые токены в `verifications` по почте из поля `value`. Это внутренний формат Better Auth, и он уже менялся (в документации упомянуты новые префиксы идентификаторов).

### 6. Сеанс: 30 дней с последнего захода

`session.expiresIn` — 30 дней, `updateAge` — сутки: при заходе срок сдвигается на 30 дней вперёд, но не чаще раза в сутки. Кеш сеанса в куке выключен (так по умолчанию), поэтому выход и истечение срока действуют сразу. Куку продлевает `proxy.ts` (решение 3). Сеансов у пользователя может быть сколько угодно. «Выйти» удаляет только сеанс этого браузера и ведёт на `/login`.

### 7. Письма: Nodemailer по одной настройке

- `src/lib/mail.ts`: `nodemailer.createTransport(process.env.SMTP_URL)`, отправитель из `MAIL_FROM`. Нет настройки — понятная ошибка при первой отправке (как с `DATABASE_URL`: сборка идёт без настроек)
- На компьютере и в тестах `SMTP_URL=smtp://127.0.0.1:1025` — Mailpit. На сервере `smtps://resend:<ключ>@smtp.resend.com:465`: Resend принимает письма по SMTP, логин `resend`, пароль — ключ API. Одна библиотека, куда слать — решает настройка
- Текст письма собирает чистая функция `buildLoginEmail(url)` → тема, HTML и простой текст; её проверяют unit-тесты. Почтовые программы не понимают CSS-переменные, поэтому цвета кнопки в письме — значения токенов из `src/styles/tokens.css`, записанные рядом с комментарием, откуда они взяты

Отвергнуто: библиотека `resend` — второй способ отправки, а спека требует Nodemailer и для заглушки, и для Resend.

### 8. Данные, которые уже есть: владелец из `OWNER_EMAIL`

Две миграции, обе создаёт drizzle-kit из схемы:

- `drizzle/0003_*.sql` — таблицы Better Auth и `login_links`. Существующие данные не трогает; с ней можно сделать и проверить вход до того, как у данных появится владелец
- `drizzle/0004_*.sql` — владелец. Порядок шагов правится вручную:
  1. `owner_id` в `contacts` и `groups`, пока без `NOT NULL`
  2. Если контакты или группы есть: почта = `lower(trim(current_setting('app.owner_email', true)))`. Пусто — `RAISE EXCEPTION` с текстом «OWNER_EMAIL is not set: existing contacts and groups need an owner». Иначе — пользователь с этой почтой (`gen_random_uuid()::text`, пустое имя, почта подтверждена; если такой есть, берётся он) и `UPDATE … SET owner_id` у всех контактов и групп
  3. `NOT NULL`, внешние ключи, новый уникальный индекс групп вместо старого, индекс `contacts (owner_id)`

Почту передаёт `scripts/migrate.ts`: читает `OWNER_EMAIL` и ставит её настройкой `app.owner_email` своего единственного соединения до запуска миграций. На сервере обе миграции придут одной выкаткой, и Drizzle применит их в одной транзакции: упало хоть что-то — база как была, выкатка останавливается, работает прежняя версия (так `deploy.sh` уже умеет). Тест миграции проверяет и это: ошибка во второй миграции не оставляет следов первой. В пустой базе (e2e, CI, новый компьютер) почта не нужна. `pnpm db:migrate` переходит с drizzle-kit на `tsx scripts/migrate.ts`, чтобы на компьютере работал тот же код, что на сервере. Миграцию показываю владельцу до merge.

Отвергнуто: почта в файле миграции — репозиторий публичный. Проставлять владельца кодом после миграций — тогда `NOT NULL` нужен второй миграцией в отдельном запуске, и они уже не атомарны. «Всё получает тот, кто войдёт первым» — первым может оказаться друг.

### 9. Демо-данные

`scripts/seed.ts` требует `OWNER_EMAIL`: создаёт пользователя-владельца, если его нет, и кладёт контакты с его `owner_id`. Если у владельца уже есть контакты — ничего не делает (сейчас проверка «есть ли контакты вообще» — станет «есть ли у владельца»). На сервере команда та же: `docker compose run --rm migrate node scripts/seed.js`.

### 10. Тесты

- Unit (Vitest, как сейчас): `parseLoginEmail`, `buildLoginEmail`
- Тесты на базе — новый набор Vitest `pnpm test:db`, файлы `src/**/*.db.test.ts`, своя пустая база `<имя>_test` (создаётся заново, как `_e2e`), `server-only` подменяется пустым модулем. Проверяют:
  - каждую функцию слоя базы с чужими номерами: B не читает, не меняет и не удаляет контакт, заметки и группы A, не отменяет его «Пообщались», не добавляет свой контакт в группу A
  - одинаковые названия групп у разных владельцев
  - лимит писем, включая два одновременных запроса и неотправленное письмо; проверку «только последняя ссылка»
  - миграции 0003 и 0004 на базе со старыми данными: базу доводят до миграции 0002, кладут данные и применяют остальное. Числа совпадают, всё у владельца; без почты при данных — ошибка, и база не изменилась (нет даже таблиц из 0003); пустая база без почты проходит
  - демо-данные у владельца
- e2e (Playwright, без моков): `e2e/login.spec.ts` — сценарии `user-auth`, `e2e/data-ownership.spec.ts` — сценарии `data-ownership` и новых сценариев `contact-groups`, в том числе критерий успеха из спеки 02 про A и B. Помощники: `e2e/mailpit.ts` (найти последнее письмо на адрес через `/api/v1/search`, достать ссылку) и вход через настоящую форму и Mailpit. У каждого теста своя почта `…-<случайное>@example.com`: свой пустой пользователь, лимит писем не мешает
  - «Прошло 15 минут», «Прошло 10 минут», «Давно не заходил» и «Захожу регулярно» — тест сдвигает время ссылки или сеанса в прошлое прямо в базе, как тесты «Пора связаться» кладут даты в прошлом. «Захожу регулярно» проверяет, что после захода срок сеанса в базе и срок куки в браузере — снова 30 дней
  - «Письмо не ушло» — режим Chaos у Mailpit: через его API SMTP начинает отказывать
  - «Запрос не из формы» — запрос прямо на `/api/auth/sign-in/magic-link`
  - Прямые запросы к действиям с чужими номерами через браузер не послать: действие вызывается по внутреннему номеру Next.js. Их проверяют тесты на базе, а действия берут владельца только из сеанса
- Существующие e2e-тесты (`main-scenario`, `keep-in-touch`, `contact-groups`) сначала входят под своим пользователем. Помощники `e2e/test-database.ts` получают владельца, счётчики считают только его контакты. Шаг «другой браузер» главного сценария входит в новом браузере под той же почтой. Тест главного сценария остаётся отдельным от тестов входа, как требует спека 02
- CI: в job `e2e` добавляются Mailpit (service-контейнер с включённым Chaos) и шаг `pnpm test:db` перед Playwright. Настройки для тестов — в `playwright.config.ts`: Mailpit, `BETTER_AUTH_URL=http://127.0.0.1:3100` и постоянный тестовый `BETTER_AUTH_SECRET`. Он не секрет: защищает только временную тестовую базу

### 11. Интерфейс

- Шапка (`src/app/layout.tsx`) читает сеанс без перехода на вход: есть сеанс — справа почта (обрезается многоточием на узком экране) и кнопка «Выйти»; на страницах входа — только логотип
- `/login`: окно `Window`, как другие экраны, заголовок «Вход», поле «Почта» (`type="email"`, `autocomplete="email"`), кнопка «Получить ссылку». У формы `noValidate`, чтобы вместо подсказки браузера было наше «Проверьте адрес почты». Вошедший уходит на `/`
- `/login/link-expired`: «Ссылка устарела, запросите новую» и кнопка «На страницу входа»
- Пустой список: подсказка «Добавьте первый контакт» вместо нынешней
- Только дизайн-токены и готовые компоненты (`Window`, `Button`, `Input`, `Field`)

### 12. Настройки

| Строка | На компьютере (`.env`) | На сервере | В тестах и CI |
| --- | --- | --- | --- |
| `BETTER_AUTH_SECRET` | случайная строка | своя случайная строка, `.env` | постоянная тестовая, `playwright.config.ts` |
| `BETTER_AUTH_URL` | `http://localhost:3000` | `https://app.context-crm.site`, прямо в `deploy/compose.yaml` | `http://127.0.0.1:3100` |
| `SMTP_URL` | `smtp://127.0.0.1:1025` | `smtps://resend:<ключ>@smtp.resend.com:465`, `.env` | `smtp://127.0.0.1:1025` |
| `MAIL_FROM` | `Личная CRM <noreply@mail.crm.context-crm.site>` | то же, прямо в `deploy/compose.yaml` | то же |
| `OWNER_EMAIL` | почта владельца | почта владельца, `.env` | не нужна: база пустая |

- `docker-compose.yml`: сервис `mailpit` (`axllent/mailpit` с точной версией, Chaos включён), порты только на `127.0.0.1`: 1025 (SMTP) и 8025 (страница в браузере)
- `deploy/compose.yaml`: новые строки в общем окружении `app` и `migrate`; обязательные помечены `:?`, как `POSTGRES_PASSWORD`. Без них compose не стартует, и выкатка останавливается до бэкапа и миграций
- `.env.example`: новые строки без значений. Если доступ к файлу закрыт настройками агента, говорю владельцу, какие строки добавить

## Risks / Trade-offs

- [Обновление Better Auth поменяет его внутренности] → опираемся только на описанное в документации, версия в `package.json` точная, e2e проходит весь вход
- [Почтовые сканеры (у некоторых почтовых сервисов) открывают ссылки из писем сами и «съедают» одноразовую ссылку] → человек увидит «Ссылка устарела» и запросит новую. Если друзья будут жаловаться — отдельная доработка: страница с кнопкой «Войти» перед входом
- [Письма Resend попадают в спам] → записи SPF и DKIM для `mail.crm.context-crm.site` по инструкции Resend; после выкатки проверяем настоящим ящиком
- [Опечатка в `OWNER_EMAIL` — данные уйдут на другую почту] → после выкатки владелец входит и видит свои данные. Если почта неверная, исправить её у этого пользователя — одна команда в базе, с согласия владельца
- [Кука привязана к адресу: `localhost` и `127.0.0.1` — разные адреса] → в `BETTER_AUTH_URL` и в README один адрес, `http://localhost:3000`
- [Каждый e2e-тест входит заново] → около секунды на тест; зато тесты не мешают друг другу данными
- [Откат стирает то, что внесли после выкатки] → `restore.sh` перед восстановлением снимает копию текущей базы, данные из неё можно достать вручную

## Migration Plan

1. До merge владелец: аккаунт Resend, домен `mail.crm.context-crm.site` подтверждён (записи DNS в reg.ru), ключ API только на отправку. В `.env` на сервере — строки `BETTER_AUTH_SECRET`, `SMTP_URL`, `OWNER_EMAIL`. Без них выкатка остановится до бэкапа: работает прежняя версия
2. До merge показываю владельцу SQL миграций 0003 и 0004 и прогон на копии локальной базы с демо-данными: числа до и после
3. Merge → выкатка: бэкап → миграции (данные получают владельца) → новый образ → smoke `/health`
4. После выкатки: числа контактов, заметок и групп совпадают с бэкапом; владелец входит и видит свои данные; вход под другой почтой — пустой список; письмо пришло в настоящий ящик
5. Откат — только вместе и только вручную, запускает владелец: сначала `./restore.sh backups/<бэкап этой выкатки>` (база возвращается к состоянию до выкатки; новая версия на старой базе выдаёт ошибки, но ничего не показывает), затем `./rollback.sh` (прошлая версия приложения). В обратном порядке прошлая версия без входа несколько минут показывала бы всем данные из новой базы. Этот порядок записываю в README
