# Design

## Context

Требования — `specs/contact-groups/spec.md`, мотивация — `proposal.md`. Сейчас в базе две таблицы, `contacts` и `notes`; форма контакта (`src/components/contact-form.tsx`) отправляется вручную через `useActionState`, чтобы при ошибке не терять введённое; главная читает `?q=` из адреса и всегда берёт свежие данные. Тестов и Vitest в проекте пока нет.

## Goals / Non-Goals

**Goals:**

- Связь «многие ко многим» между контактами и группами, без дублей и «осиротевших» записей
- Фильтр и страница групп работают без JavaScript в браузере там, где это возможно (ссылки, обычные формы), как уже работает поиск
- Одна группа не может появиться дважды из-за гонки двух запросов

**Non-Goals:**

- Порядок групп вручную, цвета и иконки групп, вложенные группы
- Массовое назначение групп нескольким контактам сразу
- Playwright и CI (по договорённости, позже)

## Decisions

### 1. Две новые таблицы

`groups`: `id` (identity), `name` (text, not null), `created_at`. Уникальный индекс по `replace(lower(name), 'ё', 'е')` — это и есть правило «без учёта регистра и без различия е/ё» на уровне базы (то же сворачивание уже используется в поиске контактов по имени, `normalizedName` в `src/db/queries.ts`), оно держится даже при двух одновременных запросах. `contact_groups`: `contact_id` и `group_id`, составной первичный ключ из них (контакт не может попасть в группу дважды), оба внешних ключа с `ON DELETE CASCADE`, индекс по `group_id` для фильтра и счётчиков.

Каскады дают нужное поведение сами: удалили группу — уходят только связи; удалили контакт — группы остаются, счётчик уменьшается. Миграция только создаёт таблицы, существующие данные не трогает.

Отвергнуто: массив `group_ids` в `contacts` — нельзя нормально переименовать и посчитать, нет внешних ключей.

### 2. Название группы

`groupNameSchema` в `src/lib/validation.ts`: trim, не пусто («Укажите название группы»), не длиннее 50 («Не длиннее 50 символов»). Повтор проверяет сервер в самом действии, но последним судьёй остаётся уникальный индекс: ошибка Postgres `23505` на нём превращается в «Группа с таким названием уже есть». Так два одновременных запроса не создадут дубль.

### 3. Форма контакта: как уходят группы

Форма отправляет два набора скрытых полей: `groupIds` (отмеченные существующие группы) и `newGroups` (названия, добавленные кнопкой «Добавить»). Читаются через `formData.getAll`. Список групп для отметок страница берёт на сервере и передаёт в форму.

Новые названия живут только в состоянии формы и создаются при сохранении, в одной транзакции с контактом: вставка контакта, `INSERT ... ON CONFLICT (replace(lower(name), 'ё', 'е')) DO NOTHING` для новых названий, выбор их `id`, затем замена связей контакта. Если контакт не прошёл проверку, ничего не создаётся. Если название совпало с существующей группой (без учёта регистра), кнопка «Добавить» на клиенте просто отмечает её, а на сервере то же самое делает `ON CONFLICT`.

Ошибка проверки возвращает поля формы как раньше; поскольку состояние отметок и новых групп хранится на клиенте и форма не пересоздаётся, введённое не теряется (сценарий «Ошибка в форме не теряет группы»). Номера групп, которых уже нет (удалили в другом браузере), сервер пропускает, а не падает.

В «Изменить» связи заменяются целиком: удалить старые, вставить отмеченные. Контактов с сотнями групп не будет, разница с diff не заметна.

Отвергнуто: создавать группу сразу по кнопке «Добавить» отдельным запросом — отмена формы оставляла бы лишние группы.

### 4. Фильтр на главной

Выбор групп — повторяющийся параметр адреса: `/?group=3&group=7&q=Иван`. Кнопки — обычные ссылки: каждая ведёт на адрес с этой группой, добавленной в выбор или убранной из него; «Все» — на адрес без `group`. JavaScript для этого не нужен.

Сервер разбирает номера через `parseContactId` (он подходит и для групп: те же правила номера), сверяет с реально существующими группами и отбрасывает остальные — так закрыт сценарий «Группа из адреса не существует» и удалённая группа в адресе. Запрос списка получает по одному условию `EXISTS (SELECT 1 FROM contact_groups WHERE contact_id = contacts.id AND group_id = N)` на каждую выбранную группу, все через `AND`: остаются только контакты, входящие во все выбранные группы. Дублей строк нет, `DISTINCT` не нужен. Условие складывается через `AND` с поиском по имени.

Блок «Пора связаться» не запрашивается, когда есть поиск или фильтр.

### 5. Страница «Группы»

`/groups` — серверная страница со списком групп и числом контактов (один запрос с `LEFT JOIN` и `count`). Переименование — небольшая клиентская форма в строке, удаление — тот же диалог подтверждения, что у удаления контакта (`AlertDialog`). Действия `renameGroup` и `deleteGroup` в `src/app/actions.ts` по образцу `updateContact` и `deleteContact`: проверка номера, понятная ошибка, `revalidatePath("/")` и `revalidatePath("/groups")`. После удаления или переименования карточки контактов обновляются сами, потому что страницы читают свежие данные.

### 6. Интерфейс

Только дизайн-токены и существующие компоненты: кнопки фильтра — `Badge`/`Button` в стиле проекта, список групп в `Window`. Для отметок групп нужен `checkbox` из shadcn/ui; он собирается из уже установленного `radix-ui`, как ранее `radio-group`, поэтому в `package.json` ничего не добавится.

### 7. Тесты

Подключаем Vitest (он в стеке `CLAUDE.md`, поэтому отдельно не согласовываем; это новая зависимость в `package.json`, о чём сказано в proposal). Тестами по TDD покрываем чистую логику: проверка названия группы и разбор номеров групп из адреса. Сценарии, которым нужны база и браузер, до появления Playwright проверяются руками по списку в `tasks.md`.

## Risks / Trade-offs

- [Случайные дубли групп из-за регистра или «е»/«ё»: «Теннис» и «теннис», «Тётя» и «Тетя»] → уникальный индекс по свёрнутому названию; название хранится так, как его ввели, сворачивается только для сравнения
- [Удалили группу в одном браузере, в другом открыта форма с ней] → номера несуществующих групп пропускаются при сохранении, контакт сохраняется без ошибки
- [Длинный адрес при выборе многих групп] → групп у одного человека десятки, а не тысячи; ограничение не нужно
- [Состояние новых групп в форме пропадёт при перезагрузке страницы] → как и любой введённый в форму текст; не хуже текущих форм

## Migration Plan

1. `pnpm db:generate` создаёт миграцию `drizzle/0002_*.sql`: только `CREATE TABLE`, индексы и внешние ключи
2. Миграция применяется отдельным шагом до старта нового образа (см. `CLAUDE.md`, раздел «Данные»)
3. Откат — только вручную, запускает владелец; данные контактов миграция не меняет
